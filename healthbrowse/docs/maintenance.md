# Operating HealthBrowse

## Source refresh

After the project and workflows reach the repository default branch and GitHub Actions is enabled, **HealthBrowse source review** checks MedlinePlus weekly on Mondays at 04:17 UTC. An operator can also trigger it manually. One successful dry run on 1 November 2026 independently reconstructed the bundled 31 October feed and all 1,017 records. The checked-in provenance manifest records its hashes. This validates the import and byte-level reproducibility. A clinical reviewer still needs to assess medical content.

The scheduled code checks the official NLM XML index, the date on the archive and its matching XML document. It rejects redirects, unknown hosts, XML entity declarations, out-of-budget files, unexpected internal files, backdated releases, coverage loss over 10%, disallowed clinical content links, and source-policy changes. The input ZIP is limited to 12 MB, XML to 60 MB and the derived asset to 4 MB. The stored source checksum detects changes and supports reproduction; it is not a publisher signature. No user data goes to the collector. The only text eligible for syndication here comes from English health-topic summary fields. MeSH terms and resource links retain attribution. [NLM feed](https://medlineplus.gov/xml.html) · [publisher usage terms](https://medlineplus.gov/about/using/usingcontent/)

1. Assign a source steward, a clinician reviewer, an engineering owner and an incident contact. Configure repository rules for default-branch review and protected release approvals. Protect the SQL migrations, authentication code, clinical source parser, source policy, data, and workflow files with code-owner review. Record actual reviewers, decision, date and release version.
2. Inspect the proposed PR. The manifest identifies added, removed, and changed topic URLs. Review the source passage in context, including age group, subtype, date, qualifier, emergency signs, and attribution. Inspect third-party links as links, without copying their target content. Record reviewed changes and any exclusions. Include publisher-correction events.
3. Approve or reject the PR. The refresh workflow cannot merge it or deploy a release. A PR created by the default workflow token may not trigger other Actions checks. The proposer therefore runs the focused integrity tests itself. Configure a review App token only if policy requires a separate downstream PR workflow. Enable **Allow GitHub Actions to create and approve pull requests** to permit PR creation; the workflow itself never approves a PR. [GitHub workflow token behavior](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/trigger-a-workflow#triggering-a-workflow-from-a-workflow)
4. On a change in substantive publisher terms or related links the job stops before downloading the feed. The source steward records the old/new rights page, new terms, allowed fields and rationale in a separate reviewed policy-change PR. Update the policy digest only after this review. A changed domain, collection, license or scraping method requires separate review. Public clinical boards do not certify our summaries merely by publishing information.
5. A terminology lookup, trial status, award or brokered research result presents its own timestamp and evidence status. Its availability does not change the governance of the weekly MedlinePlus snapshot. Add new scheduled data sources individually with owner, rights record, refresh interval, expiry handling, reconciliation tests and rollback instructions. Keep credentialed collections server-side.

From `healthbrowse/`, run `python3 scripts/maintenance_tests.py`, then `python3 scripts/maintenance_refresh.py` on a new branch, and `node --test tests/medline.test.mjs tests/seven-sections.test.mjs`. Review `git diff` before preparing a release. No scheduler runs just because a checkout exists.

## Availability and monitoring

Set repository variable `HEALTHBROWSE_PUBLIC_ORIGIN` to the production HTTPS origin after rollout. The **HealthBrowse public service probe** checks liveness, readiness and the published index four times a day. Missing configuration skips the job. An inaccessible service, unexpected redirect, invalid JSON or index older than 14 days fails the run. A failed check is a signal to investigate. GitHub's scheduler may delay jobs and is unsuitable for urgent paging; configure managed uptime alerts and an on-call destination for production. [GitHub scheduled workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

| Signal | Proposed pilot trigger | Operator response |
|---|---|---|
| Public availability and latency | Two consecutive uptime failures, or rising p95 request latency for 15 minutes | Check revision health and upstream failures, restore the previous healthy image if the release is implicated. |
| Source availability | A registry becomes unreliable or repeatedly returns errors | Display source-specific failures or dated snapshots, back off retries, and avoid treating missing records as evidence of absence. |
| Clinical quality | Any severe unsupported statement in a reviewed case | Disable the affected flow, preserve a de-identified reproducer, assign clinical review and add a regression test before release. |
| Security and privacy | Exposed credential, suspected row-level permission failure, or user data found in logs | Revoke affected access, rotate secrets, isolate the endpoint, preserve security evidence and follow the institution's incident process. |
| Cost and load | Forecast exceeds the pilot budget or instance cap is repeatedly reached | Inspect request volume, cache-hit rate and provider quotas before raising limits. Operational budget alerts alone do not cap spend. |

Collect route templates, status class, latency and anonymous aggregate upstream counts. Exclude query strings, free-text questions, access tokens, email addresses, feedback messages and precise location. Cloud request log defaults and retention require operator review. Validate under realistic mixed traffic, including cold starts, before documenting a capacity claim. Back up the database, test restore into a separate environment, and rehearse image rollbacks and app-compatible database migrations.

Security scans in CI complement dependency reviews. Review high-severity findings, assign an owner and resolution deadline, and record the reason for any exception. Test dependency and security fixes; avoid automated changes to clinical content, access policies or infrastructure limits. Publish a security contact after configuring a real monitored mailbox.
